## 1. 开源项目介绍与来源

### 1.1 ByteDance Monolith

| 项 | 内容 |
|---|---|
| 仓库 | https://github.com/bytedance/monolith |
| 维护方 | 字节跳动 |
| 定位 | 工业级**实时**推荐系统训练框架，核心是 collisionless embedding table（无冲突嵌入表）+ 在线/离线特征服务 + 实时训练 |

| 许可证（记忆中） | MIT |
| 核实状态 | **未核实** |

**它能给 Bili Daily 什么**：几乎没有可直接复用的代码。它解决的是"多用户、亿级 item、分钟级模型更新"的问题；
Bili Daily 是"单用户、个位数视频、零训练"。它对我们**唯一的价值是工程理念**：
特征与模型分离、embedding 冲突处理、实时特征更新。这些理念在本地扩展里对应的是
"画像特征与排序分离、增量更新缓存"，不需要它的代码。

**结论**：**仅借鉴公开理念，不引入代码，不作依赖。**

## 3. 推荐算法比较

评价维度按 Bili Daily 的实际约束：单用户、数据量小、纯 JS、本地运行、要可解释、不能训练大模型。

### 3.1 逐个算法

#### TF-IDF

- **原理**：词在文档中越频繁越重要（TF），在整个语料中越稀有越有区分度（IDF）。
- **在本项目的落地方式**：把每个候选 UP 主当作一个"文档"，
  词项 = 分区 + 标题字符二元组（中文不做分词，用 bigram）+ UP 主昵称片段。
- **数据需求**：需要一个"语料"（候选池）才能算 IDF，**候选池少于约 20 个时 IDF 极不稳定**。
- **成本**：极低。50 个候选 × 200 维稀疏向量，毫秒级。
- **可解释性**：强（"因为你常看科技区"）。
- **结论**：**采用**，但只在候选池规模 ≥ 20 时启用 IDF；否则退化为二值权重。

#### 余弦相似度

- **原理**：两个向量的夹角余弦，衡量方向相似而非绝对大小。
- **落地**：用户画像向量（分区占比 + 词项权重）与候选 UP 向量求余弦。
- **成本**：O(维度 × 候选数)，可忽略。
- **注意**：分区占比是**分布**，直接算余弦会忽略"用户 70% 科技 / 候选 100% 科技"这类强度差；
  建议对画像向量做 L2 归一化后使用，并额外加一个分区覆盖项。
- **结论**：**采用**。

#### 时间衰减加权

- **原理**：越久远的观看越不能代表当前兴趣。
- **落地**：在统计"用户对某分区/某 UP 的偏好"时，给每条观看乘 `0.5^(Δt / halfLife)`，
  半衰期建议 14 天（7 天窗口内权重 ≥ 0.7）。
- **注意**：C1 目前用的是**硬窗口**（7 天 / 30 天），本质是阶跃衰减。
  引入连续衰减是为了让"3 周前看了 5 个科技视频"和"昨天看了 1 个"能被合理比较。
- **结论**：**采用**，参数可配置，且必须在界面上可解释（"近 14 天权重更高"）。

#### MMR（Maximal Marginal Relevance）

- **原理**：每次选一个"与用户最相关、同时与已选结果最不相似"的候选：
  `score = λ · relevance − (1 − λ) · maxSimilarity(候选, 已选)`。
- **落地**：relevance 用第 3.1 节的打分；similarity 用候选间余弦（同分区 = 高相似）。
- **成本**：O(K² × N)，K=10、N=50 时约 5000 次点积，纯 JS 完全可接受。
- **价值**：避免推荐 10 个全是科技区 UP 主。
- **结论**：**采用**，λ 建议 0.7，仅对前 20 个候选重排后取前 5~10 个。

#### ALS（交替最小二乘）

- **原理**：把 user-item 矩阵分解成 user 因子 × item 因子，交替固定一侧求解另一侧。
- **致命问题**：**需要多用户交互矩阵**。单用户时矩阵秩为 1，分解没有意义。
- **数据需求**：实践中至少数百用户、数千交互才能稳定。
- **结论**：**不采用**（本地扩展场景结构性不适用）。

#### BPR（Bayesian Personalized Ranking）

- **原理**：用 (user, 正样本, 负样本) 三元组做 pairwise 排序学习，优化"正样本得分高于负样本"。
- **数据需求**：需要足够多的正负样本对。当前 4 个有效视频、8.9 分钟，**无法训练**；
  即使有 200 个视频，单用户的 pairwise 信号仍然极稀疏，容易过拟合到最近几天。
- **结论**：**不采用**（可作为将来 PC 端离线实验的对照，不进入产品）。

### 3.2 汇总表

| 算法 | 数据需求 | 需训练 | 需多用户 | 纯 JS | 性能 | 可解释 | 结论 |
|---|---|---|---|---|---|---|---|
| TF-IDF | 中（需候选池） | 否 | 否 | ✅ | 极低 | 强 | **采用**（候选池 ≥ 20 时启用 IDF） |
| 余弦相似度 | 低 | 否 | 否 | ✅ | 极低 | 强 | **采用** |
| 时间衰减 | 低 | 否 | 否 | ✅ | 极低 | 中（需文案解释） | **采用**（半衰期 14 天） |
| MMR | 低 | 否 | 否 | ✅ | 低（K²N） | 中 | **采用**（λ=0.7，仅重排 Top20） |
| ALS | 高 | 是 | **是** | 难 | 高 | 弱 | **不采用** |
| BPR | 高 | 是 | 是 | 难 | 高 | 弱 | **不采用** |

## 4. Edge 本地运行可行性

### 4.1 运行环境约束

- Manifest V3：禁止远程代码、`eval`；CSP 严格。
- 只有 `storage` 权限（`manifest.json` 已核实：`"permissions": ["storage"]`）。
- content script 仅在 `https://www.bilibili.com/video/*` 运行（已核实）。
- `chrome.storage.local` 默认配额约 10MB；本项目未申请 `unlimitedStorage`。
- 单线程主线程执行，任何 >50ms 的计算都会让 popup 卡顿。

### 4.2 各算法实测可行性评估（按量级推算，非基准测试）

| 项目 | 规模假设 | 估算开销 | 是否可行 |
|---|---|---|---|
| TF-IDF 建索引 | 候选 200 个 × 200 维 | 稀疏 Map 遍历，< 5ms | ✅ |
| 余弦打分 | 200 × 200 维 | < 2ms | ✅ |
| 时间衰减 | 每条观看一次乘算 | < 1ms | ✅ |
| MMR 重排 | N=50, K=10 | 约 5000 次点积，< 5ms | ✅ |
| 内存占用 | 画像 + 候选池 | 稀疏结构 < 200KB | ✅ |
| ALS / BPR | — | 需 Python 运行时或数百 KB 的 WASM/JS 训练代码 | ❌ |

> 以上是**量级估算**，不是实测。C2 正式实现时必须用 `performance.now()` 实测并写入验收报告。

### 4.3 推荐的技术形态

- 纯函数模块 `recommend.js`，形态与 `interest-profile.js` 一致：`globalThis` 挂载、无 `chrome.*` 依赖、
  可被 Node 测试直接 `require`。
- 计算放在 popup 或未来的 options 页，**不放 content script**（避免在每个视频页都跑）。
- 结果与画像一起缓存到 `chrome.storage.local` 的独立 key（不写 `biliDailyRecords`）。

## 5. 当前 C1 数据支持程度

### 5.1 现有可用特征（已核对 `content.js` / `storage.js`）

| 字段 | 来源 | 可用于 |
|---|---|---|
| `bvid`、`page` | 页面 URL / 播放器 | 去重、识别同一视频分 P |
| `title` | DOM / JSON-LD / 脚本内 `videoData` | 标题 bigram 特征 |
| `upName`、`upUid` | DOM / 脚本内 `owner.mid` | UP 主身份、候选池主键 |
| `partition` | `tname_v2` / `tname` / DOM 分区链接 | 分区特征 |
| `videoDuration` | 播放器 / `videoData.duration` | 归一化（避免长视频主导） |
| `watchMs`、`watchMsByHour` | 播放器累计 | 偏好强度、时段特征 |
| `startedAt` / `lastWatchedAt` / `updatedAt` | 本地时间 | 时间衰减 |

### 5.2 数据量现状

- 实测：**4 个有效视频、8.9 分钟、1 个有效观看日**（2026-11-11 验收）。
- 画像状态 `insufficient`。
- **这个量级不足以支撑任何"个性化排序效果"的结论**，
  只能验证"流程能跑通、降级正确"。

### 5.3 特征表达的局限

1. **分区只有一级**：B 站的 `tname` 是二级分区名（如"科技·数码"会落到具体子分区），
   不同层级混用会让向量维度噪声变大。
2. **没有标签（tag）**：B 站视频页有 `tag` 列表，但当前 `content.js` **没有采集**。
   标签是最有价值的文本特征，缺失意味着只能靠标题。
3. **标题需要中文处理**：无分词器时用字符 bigram；标题短（<10 字）时特征稀疏。
4. **没有负反馈**：只有"看了多久"，没有"划走/不喜欢"。
5. **没有多用户信号**：无法做协同过滤。

### 5.4 结论

C1 数据**足以支撑"基于分区 + 标题的画像与相似度打分"的原型**，
**不足以支撑任何学习型模型**，也**不足以证明效果优于基线**。
需要 C2 先扩充候选侧数据（见第 6 节），并积累到 **≥ 50 个有效视频、≥ 10 个 UP 主、≥ 14 个有效观看日**
再谈效果评估。

## 6. 缺少哪些候选 UP 主数据

这是 C2 的核心缺口：**画像已经有了，但"推荐的候选是谁"没有来源。**

### 6.1 当前缺口

| 需要的数据 | 现状 | 说明 |
|---|---|---|
| 候选 UP 主列表 | ❌ 无 | 本地只有"已经看过的 UP 主" |
| 候选 UP 主的分区分布 | ❌ 无 | 未看过的 UP 主没有任何本地特征 |
| 候选 UP 主的视频标签/标题 | ❌ 无 | 同上 |
| 候选 UP 主是否仍活跃 | ❌ 无 | 无法判断账号是否注销 |
| 候选 UID 的真实性 | ⚠️ 仅已看过的可信 | 来自页面 `mid`，可信；新建的不可信 |

### 6.2 可行的候选来源（按风险从低到高）

| 方案 | 数据来源 | 新增权限 | 风险 | 建议 |
|---|---|---|---|---|
| **① 回访型候选** | 本地已观看 UP 主 | 无 | 极低 | **C2 首选** |
| **② 用户手动添加** | 用户输入 UID / 空间链接 | 无 | 低 | **C2 支持** |
| **③ 视频页"相关推荐"DOM** | 用户已在浏览的视频页上已渲染的推荐卡片 | 无（content script 已在该页面运行） | 中：结构变更、ToS 边界 | **C2 可选，默认关闭，需用户显式开启** |
| **④ 排行榜页 / 搜索页采集** | 需要扩展 content script 覆盖面 | **需要修改 matches** | 中高 | **不做**（超出本次授权） |
| **⑤ 调用 B 站公开 API** | `api.bilibili.com/...` | **需要 host 权限 + 网络请求** | 高：接口未公开承诺、可能触发风控、可能违反 ToS | **不做** |

> **明确声明**：本报告**不假设** B 站提供任何"官方推荐 API"。第 ⑤ 项仅作为"不可行选项"列出。

### 6.3 候选 UID 的真实性保证

1. **只从页面已渲染的链接 / 已解析的 `owner.mid` 读取**，不构造、不猜测、不做算术推导。
2. 存候选时同时存 **出处**：`source`（watched / manual / related-dom）、`sourceBvid`、`observedAt`。
3. **去重**：按 `upUid` 去重；无 UID 的候选（只有昵称）单独标记 `uidVerified: false`，不参与主排序。
4. **失效处理**：候选在页面上不再出现时，把 `lastSeenAt` 更新为观察时间；
   超过 90 天未再观察到，降权但不删除（避免误判）。
5. **不可靠候选**：昵称为空、UID 非正整数、UID 与昵称在同一页出现矛盾时，标记 `unreliable: true` 并排除。

## 7. 最终推荐算法组合

### 7.1 分层架构

```
本地观看记录 (chrome.storage.local: biliDailyRecords)
        │  只读
        ▼
[C1] 用户兴趣画像  (interest-profile.js, 已完成)
        │  分区分布 + UP 聚合 + 覆盖率 + 状态
        ▼
[C2] 候选召回  (recommend-candidates.js, 待做)
        │  候选池: {uid, name, source, provenance, features}
        ▼
[C3] 个性化排序  (recommend-rank.js, 待做)
        │  打分 → 时间衰减 → MMR → TopK
        ▼
推荐结果展示  (popup「猜你喜欢的 UP 主推荐」卡片, 已存在占位)
```

### 7.2 用户兴趣特征从哪里来

**全部来自 C1 画像，不新建统计口径**：

- 分区偏好：`windows["30d"].partitions[].share`
- UP 偏好：`windows["30d"].ups[]`（含 `watchMs`、`effectiveVideoCount`）
- 数据充分度：`status` / `reasons` / `partitionCoverage.ratio`
- 时段偏好：`watchMsByHour`（可选，用于"晚上更适合看什么"这类弱特征）

### 7.3 候选从哪里来

按第 6.2 节：**① 回访 + ② 手动添加**为 C2 基线；**③ 相关推荐 DOM** 作为可选增强，默认关闭。

### 7.4 特征与打分公式（建议）

```text
用户向量 u:
  分区维 p_i = 30 天内该分区观看时长占比（含「未知」桶，但「未知」不参与匹配）
  词语维 w_j = 标题 bigram 的 TF-IDF（候选池 IDF），按时间衰减加权

候选向量 c(UP):
  分区维 = 该 UP 被观察到的视频所属分区的加权分布（未观察到的候选为 0）
  词语维 = 该 UP 相关标题的 TF-IDF 质心

分区匹配度  S_part = cos(u_part, c_part)
内容相似度  S_text = cos(u_text, c_text)
熟悉度      S_fam  = 该 UP 在 30 天内的观看时长 / 总时长（回访型候选显著更高）
新鲜度      S_new  = 1 - 最近一次观看距今的天数 / 90（长期未看加分，刚看过降分）
数据可信度  S_trust= uidVerified ? 1 : 0.3

总分 = 0.45·S_part + 0.25·S_text + 0.20·S_fam + 0.10·S_new，再乘 S_trust
```

> 权重是**先验设定**，不是调优结果。C3 必须用离线实验对比基线后再定，禁止在报告里声称"提升 X%"。

### 7.5 时间衰减怎么引入

- 在计算 `u` 时，每条观看按 `0.5^(Δt/14天)` 加权，而不是只用 7/30 天硬窗口。
- 在 `S_new` 中用连续函数表达"太久没看"。
- 半衰期写入配置常量，界面上以文案说明，避免"黑箱"。

### 7.6 MMR 怎么控制多样性

- 先对全部候选打分排序，取 **Top 20**。
- 对 Top 20 做 MMR，`λ=0.7`，候选间相似度用 `cos(c_i, c_j)`（分区 + 文本）。
- 输出 **Top 5**（popup 空间有限，5 条足够）。
- 每条结果附**解释**：`"你近 30 天 69% 的观看在科技区"` / `"你最近没怎么看这个 UP 主"`。

### 7.7 数据不足时怎么降级

| 画像状态 | 行为 |
|---|---|
| `empty` | 不展示推荐；文案"继续观看以生成推荐" |
| `insufficient` | **只展示回访候选**（已看过的 UP 主按近期观看时长排序），文案"数据较少，以下是你常看的 UP 主"；**不做相似度打分，不说"猜你喜欢"** |
| `ok` 但候选池 < 20 | 关闭 IDF，退化为二值权重；仍展示但不强调"个性化" |
| 候选池为空 | 展示"暂无候选，可在视频页开启候选采集或手动添加" |

> 这条降级规则是本次调研最重要的产品结论：**当前 4 个视频的状态就是 `insufficient`**，
> 所以 C2/C3 的第一个可交付版本实际上只会展示"回访列表"，必须先接受这一点。

## 9. 算法评估与验收标准

### 9.1 离线对比方案（未来可执行）

**数据切分**：把观看记录按时间切分为"训练段"与"测试段"。
建议：以最近 7 天为测试段，之前 30 天为训练段；每 7 天滚动一次，做多次切片以增加样本。

**对比方法（必须全部实现，否则无法判断收益）**：

| 编号 | 方法 | 说明 |
|---|---|---|
| B0 | 热门基线 | 按 30 天观看时长排序的 UP 主 |
| B1 | 分区匹配基线 | 只按分区占比匹配，不看文本 |
| M1 | TF-IDF + 余弦 | 分区 + 标题 bigram |
| M2 | M1 + 时间衰减 | 半衰期 14 天 |
| M3 | M2 + MMR | λ=0.7，Top20 → Top5 |

**指标**：

- `HitRate@K`：测试段实际观看的 UP 主是否出现在 Top K；
- `Precision@K` / `Recall@K`；
- `NDCG@K`：考虑排序位置；
- `Coverage`：推荐覆盖的 UP 主占候选池比例；
- `IntraListSimilarity`：列表内平均相似度，越低越多样；
- 运行耗时（`performance.now()`）。

**适用条件与局限（必须写进评测脚本注释）**：

1. 单用户、样本少，**指标方差极大**，不能用单次结果下结论；
2. 测试段"没看"不等于"不喜欢"，缺负样本；
3. B0 基线在数据量极小时常常**打败**复杂方法，这是正常现象，不是 bug；
4. 数据量 < 50 个有效视频时不建议跑评测，结果无统计意义；
5. **禁止**在报告中把离线指标说成线上效果。

### 9.2 验收标准（C2/C3 各阶段）

| 阶段 | 验收标准 |
|---|---|
| C2-1 | 单元测试覆盖：空候选、重复 UID、无 UID 候选、来源标记；纯函数；不写存储 |
| C2-2 | 失效候选降权但不误删；矛盾记录标记 `unreliable`；快照前后一致 |
| C2-3 | TF-IDF 在 1 篇文档 / 0 词 / 全相同词时不死锁不除零；结果可复现 |
| C3-1 | 打分在 0~1；时间衰减单调；参数可配置 |
| C3-2 | MMR 输出无重复、多样性指标不低于基线；解释文案与数据一致 |
| C3-3 | popup 不因推荐失败而白屏；`insufficient` 时展示回访列表 |
| C3-4 | 评测脚本可复现；输出基线对比表；不硬编码结果 |
| 全局 | 82 项既有测试仍全部通过；无新增权限；`biliDailyRecords` 不被写入 |

## 10. 风险与待解决问题

### 10.1 技术风险

1. **候选数据来源缺失**是整个 C2 的最大瓶颈，比算法选择重要得多。
2. **单用户 + 小样本**：任何学习型方法都不可靠；启发式 + 可解释是唯一现实选择。
3. **中文标题特征稀疏**：无分词器时 bigram 效果有限，短标题近乎无特征。
4. **分区粒度不一致**：`tname` / `tname_v2` 层级混用会污染向量。
5. **存储配额**：候选池持续增长，需设计上限与淘汰策略（建议 ≤ 500 个候选）。
6. **性能**：当前估算是量级推测，必须实测。

### 10.2 产品风险

7. **"猜你喜欢"承诺过高**：4 个视频的数据不可能产生好推荐，界面文案必须诚实降级。
8. **新鲜感疲劳**：回访型候选容易让推荐变成"最近看过的列表"，需要 MMR 与新鲜度项缓解。
9. **解释的准确性**：解释文案必须由实际特征生成，不能模板化编造理由。

### 10.3 合规与隐私风险

10. **B 站服务条款**：页面结构采集属于灰色地带，默认关闭、用户显式开启、只读本地使用。
11. **隐私**：所有计算本地完成，不上传；公开分享推荐结果前需提示可能暴露观看偏好。
12. **许可证**：三个开源项目本次均**未核实**，进入编码前必须完成第 2.5 节清单。

### 10.4 待用户确认的问题

1. **C2 是否接受"回访型候选"作为第一版**（不做任何页面采集）？
2. **是否允许 C2-4 的"视频页相关推荐 DOM 采集"**（默认关闭 + 明确开关）？
3. **推荐结果的展示位置**：popup 现有占位卡片，还是新建独立页面？
4. **是否需要"手动添加 UP 主"**功能（会引入输入校验与 UID 真实性判断）？
5. **隐私文案**：是否同意在首次使用推荐时弹出"本地计算、不上传"的一次性说明？
