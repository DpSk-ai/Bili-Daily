## 问题 A：可靠性与相似度混合

### A.1 问题

C3-0 §3.9 的公式：

```
S = Σ (w_i · r_i · s_i) / Σ (w_i · r_i)
```

其中 `r_i` 是可靠性（由覆盖率导出）。当**只有一个可用组件**时，

```
S = (w · r · s) / (w · r) = s
```

可靠性被分子分母同时约掉，**完全不生效**。这意味着：

- 数据覆盖率极低的候选与覆盖率高的候选得到相同的最终分；
- 而多组件时可靠性又会改变相对权重——同一概念在两种情形下语义不一致。

这是一个真实的公式缺陷，不是实现细节。

### A.2 修正：三层分离

把原本被揉进一个标量的三件事拆开：

| 层 | 含义 | 取值 | 归属阶段 |
|---|---|---|---|
| `similarity` | 两个向量在数学上的相似程度 | `[0,1]` 或 `null` | **C3-1 实现** |
| `coverage` | 该相似度建立在多少有效数据上 | `[0,1]` 或 `null` | **C3-1 输出** |
| `confidence` | 综合证据质量后的可信等级 | 分级 + 原因 | **C3-2 决定** |

规则：

1. `similarity` **不再乘任何可靠性因子**——它就是纯余弦；
2. `coverage` 作为独立字段随结果输出，注明统计口径（`watch-ms` / `video-count`）；
3. `confidence` 的分级规则**推迟到 C3-2**，C3-1 只提供计算所需的输入
   （两侧 coverage、可用性、缺失原因），并输出
   `confidencePolicy: "deferred-to-c3-2"`；
4. C3-1 **不产出**任何"最终综合分"。

### A.3 C3-2 的建议方向（未实现，仅记录）

- 用覆盖率对相似度做**收缩**（shrinkage）而不是乘除抵消，例如
  `s' = λ(cov) · s + (1 − λ(cov)) · prior`，其中 `λ(cov)` 单调递增；
- 或者把 `confidence` 作为**展示层**信息（"数据较少"），不进入排序数值；
- 具体选择必须由 C3-4 的离线对比决定，C3-1 不做预设。

### A.4 对 C3-0 相关段落的替代

| C3-0 原文 | 替代规则 |
|---|---|
| §3.8 `r_P / r_T` 乘在相似度上 | 取消乘法；覆盖率只作为元数据输出 |
| §3.9 `S` 公式 | C3-1 不实现 `S`；C3-2 重新设计 |
| §7.1 `confidence` 由覆盖率导出 | 导出规则推迟到 C3-2 |

## 问题 B：跨统计口径比较

### B.1 问题

现网数据里，分区权重有三种不同口径：

| 来源 | 口径 |
|---|---|
| 用户侧（观看记录） | `watch-ms` |
| C2-3 main lane 候选 | `watch-ms`（`shareOfIdentified` 的分母是已识别分区观看时长） |
| C2-4B exploration lane 候选 | `video-count`（`shareOfImportedVideos` 的分母是可用视频数） |

余弦在数学上可以计算任意两个同维向量，但 `watch-ms` 与 `video-count` 的
**语义不同**：前者表达"投入时间"，后者表达"内容构成"。把两者直接比较，
结果没有明确含义，且容易在数值上看起来"很正常"，从而被误当作有效结论。

### B.2 修正：显式 basis + 默认拒绝

1. **每个向量对象必须带 `basis` 字段**：`"watch-ms"` / `"video-count"` / `"token-count"`；
2. **默认禁止跨口径比较**：
   - 两侧 `basis` 不同且都不是 `"unspecified"` → 比较结果为 `status: "cross-basis-rejected"`，
     `similarity: null`，`cosineSimilarity()` 返回 `null`；
3. **显式近似**：只有调用方传入 `allowCrossBasis: true` 时才计算，并返回
   - `status: "approximation"`
   - `approximate: true`
   - `bases: { left, right }`
   - `limitations: [...]`（说明哪一侧是什么口径、为什么不可等价）
4. **近似结果不得与同口径结果混排或直接比较**；
5. **C3-1 不混合两条 lane 的最终评分**——本阶段根本没有最终评分。

### B.3 无法消除的近似

用户侧永远只有观看时长，导入侧永远只有视频个数。因此 exploration lane 的分区相似度
**本质上只是近似**，C3-1 能做的只有：

- 让它在类型系统层面显式（`approximate: true`）；
- 让调用方必须主动声明（`allowCrossBasis`）；
- 在输出里写清限制，供 C3-2 降级使用。

## 问题 C：近期性公式与重复推荐抑制

### C.1 问题

C3-0 §4.4 用"刚看过就压低 `S_rec`"来避免推荐列表变成"最近观看复制"。
但这里混了两个不同概念：

| 概念 | 回答的问题 | 正确做法 |
|---|---|---|
| **近期性（recency）** | 用户最近的兴趣是否比很久以前更重要？ | 对**用户侧历史证据**做时间加权，是"兴趣漂移"建模 |
| **重复曝光抑制（re-exposure suppression）** | 刚推荐/刚看过的 UP 主是否应该降低展示频率？ | 对**已经出现过的结果**做扣减，是"列表新鲜度"策略 |

两者作用对象不同：前者作用在**输入侧的观看记录权重**，后者作用在**输出侧的候选分数**。
若都用同一个"距今天数"公式表达，会导致：

- 用户越久没看某 UP 主，兴趣证据越弱（近期性），但重复曝光抑制却要求"越久没看越该推"；
- 两个方向相反的意图被同一个变量驱动，调参时必然互相打架。

### C.2 修正

1. **C3-0 §4.4 中"S_rec / 已看过候选抑制"的表述作废**；
2. C3-2 将**分别**设计：
   - `interestDecay(record)`：作用于用户向量的每条观看记录（半衰期参数）；
   - `reExposurePenalty(candidate, exposureHistory)`：作用于排序后的候选，
     依赖"最近推荐过什么"的本地记录（尚不存在，需要单独设计存储）；
3. 两者的参数、测试与解释文案**互不复用**；
4. **C3-1 不实现任何一个**——本阶段的用户向量使用原始计数/原始观看时长，
   输出中明确写 `decay: "none"`、`weighting: "raw-count"` / `"watch-ms-raw"`。

### C.3 对 C3-1 的约束

C3-1 的用户向量构建函数保留一个**记录权重钩子**（`options.recordWeight`），
默认 `null`，即原始计数。该钩子只是接入点：

- 默认路径不引入任何时间概念；
- 传入自定义权重时，输出 `weighting: "custom-record-weight"` 以便审计；
- C3-2 的衰减函数将通过该钩子接入，而不是修改 C3-1 的函数签名。
