1.2 expected 与 actual 的差异

失败发生在第 828 行（node:assert 报告位置 test-candidate-content-import.js:828:10）。按 Node 的 + actual / - expected 标记，差异为：

   url: '',
-  urlState: undefined      ← expected（原始 sidecar）中存在该键
   }                          ← actual（JSON 往返后）中该键消失
  • expected：sidecar.candidates[*].videos[*] 含键 urlState，值为 undefined。
  • actual：JSON.parse(JSON.stringify(sidecar)) 中该键不存在。

原因在于 JSON.stringify 的规范行为：对象自有属性若值为 undefined，会被直接省略。于是“往返”丢掉了这个键，deepEqual 判为不等。

C2-4B-test-debug.txt 中三个视频（BV1xx411c7mD / BV1yy411c7mD / BV1zz411c7mD）逐个重复了同一行差异，与上述判断一致。

2. 根本原因

调用链：

parseVideo(raw, ...)        → 返回 { bvid, title, partition, tags, url, urlState }   ✅ 有 urlState
   ↓ variants.push(video)
resolveVideo(bvid, variants) → 返回 { bvid, title, partition, tags, url,
                                      titleState, partitionState, titleTruncated,
                                      status, conflictFields }                      ❌ 漏了 urlState
   ↓
buildCandidateEvidence(...)  → videos.map(v => ({ ..., urlState: v.urlState, ... }))  → undefined

candidate-content-import.js 中 urlState 只出现两处：

行位置作用
512parseVideo 返回对象写入 urlResult.state
1081buildCandidateEvidence 映射读取 video.urlState

中间的合并层 resolveVideo() 既没有透传也没有重算 urlState。因此只要走“解析 → 去重合并 → 构建证据”这条主链路（即所有正常调用），sidecar 里的每个视频都会得到 urlState: undefined。

2.1 为什么判定为业务实现缺陷

docs/acceptance/C2-4B/C2-4B-import-report.md 第 2.4 节明确规定 sidecar 视频结构为：

bvid, title, partition, tags, url, urlState,
titleState, partitionState, titleTruncated,
status: "usable" | "metadata-conflict" | "uid-conflict",
conflictFields

其中 urlState 的取值域为 "missing" | "accepted" | "rejected" | "short-link" | "not-video-url"。

也就是说：sidecar 缺少 urlState 本身就是违反已确认设计规范的，第 46 项只是把这个问题暴露出来的那个断言。按“优先只改业务实现”的要求，正确修法是补上实现，而不是放宽测试。

可能性结论依据
排序不稳定排除差异是“键存在 vs 键不存在”，与顺序无关；第 47 项（顺序无关）此前通过

3.1 新增：确定性的 URL 状态合并规则

const URL_STATE_PRECEDENCE = [
  "accepted",
  "short-link",
  "not-video-url",
  "rejected",
  "missing"
];

function resolveUrlState(url, states) {
  if (url) return "accepted";
  for (let i = 0; i < URL_STATE_PRECEDENCE.length; i += 1) {
    if (states.has(URL_STATE_PRECEDENCE[i])) return URL_STATE_PRECEDENCE[i];
  }
  return "missing";
}

规则语义：

  1. 只要任一变体提供了合法 URL（此时 url 已是去参数的规范地址），合并结果为 accepted；
  2. 否则按固定优先级取第一个实际出现过的状态，保证与输入顺序无关（复用第 47 项的约束）；
  3. 全部未提供才是 missing。

4. 为什么修复不会破坏既有功能

  1. 只补字段，不改判定：urlState 是描述性字段，不参与 usableVideoCount、partitionCoverage、titleCoverage、contentStatus 或 eligibleForExploration 的任何计算。内容的取舍仍完全由 computeContentFeatures() 依据 status / title / partition 决定。
  2. 不改变去重与冲突语义：title / partition / tags / url 的合并逻辑一行未动，metadata-conflict、uid-conflict 的判定条件未变。
  3. 确定性：新增规则只用固定优先级表与集合，不含时间、随机数或输入顺序依赖，与第 47 项“输入顺序变化不改变输出”一致。
  4. 不修改入参：仍在合并阶段新建对象，不写回调用方传入的导入文档（第 45 项要求深度冻结仍可处理）。
  5. 跨模块隔离：全项目只有 test-candidate-content-import.js 引用本模块，其余 7 个测试文件不依赖它，因此既有 181 项的行为不受影响。
  6. 值域不扩大：新增输出值只可能落在设计文档规定的 5 个枚举内，不会引入新状态。
