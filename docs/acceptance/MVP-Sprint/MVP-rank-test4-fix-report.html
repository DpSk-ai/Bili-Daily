2. 定位过程

2.1 测试 fixture

baseRecords() 提供 7 条观看记录（科技 4 条、生活 1 条、知识 2 条），buildRecommendations({ now, endDate: D1, K: 5 }) 走相似度路径，UP 1001 的推荐理由为 watched-before + partition-match（第 192-195 行断言已通过）。

2.2 实际 true 的来源

对返回对象做字符串搜索，命中位置只有一处，不在 reasons 里：

// recommend-rank.js:1029-1032（修复前）
note:
  "推荐基于本地观看记录与用户主动导入的候选资料，本地计算、不上传；" +
  "不代表平台核验，也不构成推荐准确率声明。"

JSON.stringify(result) 序列化了 result.note，其中包含“准确率”三个字。触发 true 的是这句否定式免责声明，不是任何推荐理由或证据字段。

2.3 排除其他可能

候选来源是否进入 JSON.stringify(result)是否含“准确率”
buildReasons() 生成的四类理由是否（代码逐条核查）
entry.reliability 完整对象否（toRecommendation 只取 level / 覆盖率）—
Quality.assessFeatureReliability().note否含，但未被序列化
coldStart / diagnostics / config是否
result.note是是 ← 唯一命中

全仓库检索 准确率：业务代码中只有 recommend-rank.js 的两处（顶部注释与 note）以及 recommend-quality.js 的两处（注释与可靠性 note，均不进入本结果）。

2.4 问题分类

属于“测试预期与提示文案冲突”，不是业务逻辑错误，也不是推荐证据字段错误。

  • 业务规范：不得虚构“准确率 / 已认证 / 官方推荐”。
  • 测试实现：用三个粗粒度子串检查守护该规范，覆盖整个结果 JSON。
  • 冲突点：结果中的否定式免责声明（“不构成……声明”）恰好包含了被禁词。
  • 理由与证据本身是真实字段：watched-before 的 watchedVideoCount = 2、partition-match 的 userShare 与 candidateShare 均来自实际观看统计，第 195 行断言已通过。

因此不存在“虚构用户分区偏好 / 虚构标题匹配 / 虚构观看记录 / 虚构认证状态”的问题。测试断言本身符合业务规范，不需要也不允许把 false 改成 true。
