3. 最终工程审计

3.1 manifest 权限与匹配范围

项目实际值评价
Manifest 版本MV3符合当前 Edge 扩展模型
permissions["storage"]仅本地存储，无 tabs、history、cookies、downloads
host_permissions未声明无跨站访问权限
content script 匹配https://www.bilibili.com/video/*只进入视频页，不进首页、动态、直播、个人空间
content script 文件storage.js、discovered-candidate-store.js、candidate-discovery.js、content.js依赖顺序固定
background / service worker无无常驻后台
web_accessible_resources无不向页面暴露扩展资源
version0.0.1未在封版时修改；见第 10 节建议

结论：权限面很小，符合“个人自用、本地记录”的定位。storage 权限本身可读整个扩展的chrome.storage.local，但代码只访问第 7 节列出的四个键。

3.2 自动发现开关与默认值

  • 默认关闭，用户必须主动开启；没有“首次安装自动开启”的逻辑。
  • 开关状态写入独立键，不混入观看记录或导入批次。
  • 关闭后，内容脚本的 syncSettings() 调用 stop()，断开 MutationObserver、清理定时器与监听器。
  • addObservations() 在 settings.enabled !== true 时返回 disabled: true 且不写存储。
  • 弹窗在设置读取失败或存储读取失败时禁用开关，避免误写。

3.3 page-observed 来源标识

  • candidate-discovery.js 与 discovered-candidate-store.js 均固定：PROVENANCE = "page-observed"、SCOPE = "related-recommendation-card"。
  • 存储层注释明确：绝不复用 user-provided，固定 onlineVerified: false。
  • 推荐卡会显示「页面相关推荐发现」徽标；推荐理由使用 page-observed 理由码，文案明确“本地观察、未在线核验、不代表平台认证”。
  • 证据适配输出 identityEvidence.sources = ["page-observed"]。

3.4 已观看候选与陌生候选的区分

  • 自动发现适配层从 biliDailyRecords 收集已观看 UP UID，并将这些 UID 从观察候选中排除（collectWatchedUids → 冲突/排除逻辑）；统计中单独记录 watchedUpExcluded。
  • 推荐分两条通道：
  • main：本地观看记录中的回访 UP 主，理由是 watched-before，可带真实观看视频数与时长。
  • exploration：未在本地观看过的候选，来源只能是 user-provided 或 page-observed。
  • 跨通道同 UID 去重时 main 优先，避免同一个 UP 主同时以“看过”和“陌生”出现。

3.5 UID / BV 去重与冲突阻断

  • 观察记录以 UID|BV 合并；同一 UID + 同一 BV 重复观察只保留一条并更新时间。
  • 同一 BV 出现不同 UID：标记 uid-conflict，记录 conflictUids；冲突候选不进入探索通道，界面提示“待人工复核，不会进入推荐”。
  • 同一 UID 跨来源（手动导入 + 页面观察）：排序层用导入 UID 集合排除自动发现同 UID，手动导入优先，最终推荐中只出现一次。
  • 同一 BV 同 UID 但标题/分区矛盾：不采用矛盾标题，按元数据冲突处理。
  • 导入批次内部也做 UID/BV 校验；无效观察整条拒绝，不因一条坏数据写入空存储。

3.6 导入数据与自动观察数据隔离

四个存储键彼此独立：

键写入方内容
biliDailyRecordsstorage.js / content.js观看记录
biliDailyCandidateImportscandidate-store.js用户主动确认导入的批次
biliDailyDiscoveredCandidatesdiscovered-candidate-store.js页面观察候选
biliDailyDiscoverySettingsdiscovered-candidate-store.js自动发现设置
  • discovered-candidate-store.js 只写后两个键；观看记录仅作为只读输入传入，用于排除已观看 UP。
  • 自动发现不写 biliDailyCandidateImports，导入也不写 biliDailyDiscoveredCandidates。
  • 删除/重建自动发现候选不会删除导入批次；清除操作只清空观察候选，设置保持开启（测试 25）。

3.7 推荐理由真实性

  • watched-before：使用真实 watchedVideoCount 与 watchedWatchMs，文案给出视频数与约分钟数。
  • page-observed：使用真实 importedVideoCount（观察到的不同视频数），明确说明“本地未观看过”与“不代表账号经过平台验证”。
  • user-imported：使用真实导入视频数，明确“未经平台在线核验”。
  • 分区/标题匹配理由只在确实存在对应向量与相似度时生成；覆盖不足时使用 low-coverage。
  • 代码中多处明确写明“证据等级是工程启发式，不是概率，也不是预测准确率”；未发现“官方认证”“已验证准确率”等虚假表述。
  • 限制：理由描述的是证据来源与匹配依据，不是对推荐质量的保证。

3.8 是否存在意外的远程发送路径

静态核对结果：

  • 运行代码中未发现 fetch(、XMLHttpRequest、WebSocket、sendBeacon、chrome.runtime.sendMessage、chrome.cookies、document.cookie。
  • manifest.json 无 host_permissions，无远程脚本、无外部样式、无 CDN 依赖。
  • 代码中出现的 https://www.bilibili.com/... 与 https://space.bilibili.com/... 仅用于：
  • 解析页面链接中的 BV / UID；
  • 生成推荐卡跳转链接（经 UID 正则校验后使用）。
  • 报告生成脚本 tools/build-report-html.js 只读本地 Markdown、写本地 HTML，不联网。
  • 测试 test-auto-discovery-integration.js 第 20 项会对五个关键文件做同样的静态字符串检查。

结论：未发现扩展主动向远程发送用户数据的路径。 这是静态审计结论，不是网络抓包或全面安全审计。

3.9 内容脚本的观察器与性能

项目实际实现评价
MutationObserver 数量每个控制器最多 1 个；started 防重入，重复 start() 直接返回未发现重复观察器
观察回调只调用节流 schedule()，不在回调内遍历 DOM避免同步回调抖动
节流变更延迟 700 ms；两次扫描最小间隔 1500 ms有明确上限
扫描范围每次最多 400 个锚点、40 张卡片；每页最多 100 条观察有硬上限
页面检查2 s 检查一次 URL 变化（仅开启自动发现时）轻量
暂停页面隐藏时跳过扫描；pagehide 停止降低后台开销
观看记录content.js 每 1 s 执行一次 sync()；每次会查询主 <video> 并读取页面元数据既有设计，不是 DOM 观察器；属于可优化点，未在本轮实测 CPU
性能测试400 卡片扫描、300/500 条证据适配，单次阈值 5 s合成数据、宽阈值，只能发现明显退化，不能证明真实页面流畅

结论：未发现“重复观察器”这一明显缺陷；存在一个既有的 1 秒轮询（每次读取视频元素与页面元数据），长期 CPU/内存影响未测量，建议下一版本改为事件驱动或降低空闲时的读取频率。封版未改动。真实 B 站页面的长跑性能、SPA 切换、多标签页并发均未验证。

3.10 HTML 是否安全渲染不可信文本

  • popup.js 明确不使用 innerHTML；所有外部文本（UP 名称、分区、导入文件名、推荐理由）通过 textContent 写入。
  • 推荐卡链接只接受 safeSpaceUrl() 校验后的 https://space.bilibili.com/<uid>，且 UID 必须与候选 UID 一致；链接带 rel="noopener noreferrer"。
  • 存储层对文本做控制字符清理、长度截断和字段白名单；恶意额外字段不会进入存储（测试 8）。
  • 报告生成脚本在插入 Markdown 文本前统一 escapeHtml，转义 & < > "。
  • 未发现 eval、new Function、document.write、insertAdjacentHTML。

结论：当前渲染路径使用安全 DOM API，未发现明显的 HTML 注入面。

6.2 已知限制

  • 自动发现只读取“页面已经渲染出来”的相关推荐卡片，不自动滚动、不自动点击、不批量打开视频；懒加载或未渲染的卡片不会被发现。
  • 观察数据有保留期（默认 180 天）和容量上限（默认 300，硬上限 500）；旧数据会被裁剪。
  • 探索通道的分区相似度存在跨口径近似，统一按低可信度处理。
  • 标题匹配是无语义的 token/bigram 相似度，不理解内容含义。
  • 冷启动门槛（50 个有效视频、14 个活跃日等）来自调研与实验值，不是实测最优参数。
  • 推荐理由只解释“为什么出现”，不保证“推荐一定合适”。
  • content.js 每秒执行一次元数据同步，长时间停留视频页时的 CPU 影响未测量；这是既有实现，封版未改动。

7. 本地数据键与备份注意事项

7.1 数据键

键内容是否包含在扩展目录快照中
biliDailyRecords观看记录（按日期、BV 组织）否
biliDailyCandidateImports手动导入的候选批次否
biliDailyDiscoveredCandidates页面观察候选否
biliDailyDiscoverySettings自动发现开关与容量配置否

扩展目录备份不等于用户数据备份。 快照只包含代码、测试和文档；真实数据在 Edge 的 chrome.storage.local（LevelDB）中，不在 D:\Bili-Daily 的任何目录里。

7.2 数据导出方案（需用户本人操作）

Claude 本轮没有读取或覆盖真实存储。建议用户在需要时手动导出：

  1. 打开 Bili Daily 弹窗。
  2. 在弹窗内右键 →「检查」打开 DevTools。
  3. 在 Console 中执行（只读，不修改数据）：
chrome.storage.local.get(null, (all) => {
  const text = JSON.stringify(all, null, 2);
  console.log(text);
  copy(text); // 复制到剪贴板
});
  1. 粘贴到本地文本文件，例如 D:\Bili-Daily-data-backup\bili-daily-storage-2026-11-12.json，不要放进扩展目录快照。

7.3 数据恢复方案（需用户确认后执行）

恢复会覆盖同名键，执行前必须先完成 7.2 的导出并确认文件内容。

  1. 打开弹窗 DevTools Console。
  2. 把备份 JSON 赋给变量：
const backup = { /* 粘贴 7.2 导出的完整 JSON */ };
chrome.storage.local.set(backup, () => console.log("restored"));
  1. 关闭并重新打开弹窗，确认观看记录、导入批次、自动发现候选数量与备份一致。
  2. 若只想恢复部分键，先 delete backup.biliDailyDiscoveredCandidates 等，再执行 set。

7.4 Edge 配置目录级备份（可选，风险更高）

真实数据通常位于 Edge 用户配置下的扩展 Local Extension Settings 目录，例如 %LOCALAPPDATA%\Microsoft\Edge\User Data\Default\Local Extension Settings\<扩展ID>。这是 LevelDB 目录，必须在 Edge 完全退出后整目录复制；不要在运行中复制，也不要用它覆盖正在使用的数据。该方式依赖扩展 ID，恢复后 ID 不一致则无效。普通用户优先使用 7.2/7.3 的显式 JSON 导出。

7.5 注意事项

  • 卸载扩展、删除 Edge 用户配置、切换 Edge 配置文件都可能使数据不可见。
  • 不要把 biliDailyRecords 等键写进扩展目录快照，也不要在快照恢复命令中触碰它们。
  • 恢复代码（第 9 节）与恢复数据（7.3）是两件独立的事，先后顺序建议：先备份数据 → 再恢复代码 → 重载扩展 → 确认数据仍在。

10. 后续开发建议

按优先级排列，均为下一版本的工作，不在本次封存中执行：

  1. 配置 Git 并提交当前冻结版本：以本快照为基线建立首个提交与标签，之后所有改动可追踪。
  2. 发布卫生：把 dev-config.js 的 enabled 改为 false，移除开发日期入口；同时把 manifest.json 的 version 从 0.0.1 提升到明确的个人版本号（如 1.0.0）。
  3. 数据导出/恢复 UI：在弹窗内提供显式导出/导入按钮，避免依赖 DevTools 控制台；导出内容应带 schema 版本与时间戳，导入前预览差异。
  4. 长期稳定性观察：连续使用 1–2 周，记录候选数量、存储增长、弹窗打开耗时、多标签页下的内存占用；发现异常再优化，不预先重构。
  5. 真实推荐评估：记录推荐曝光与是否点击/观看，做简单的离线命中率统计；不要把“可信度”当作准确率。
  6. B 站 DOM 兼容维护：定期在真实视频页检查相关推荐卡片结构；观察器已尽量避免依赖固定类名，但页面结构变化仍可能降低发现率。
  7. 性能测量：在真实页面上记录 MutationObserver 回调频率、扫描耗时、写入频率；合成测试的 5 秒阈值只用于发现明显退化。
  8. 数据恢复演练：在非关键数据上实际走一遍 7.2/7.3，确认 JSON 备份可恢复后再依赖它。
  9. 保持冻结：任何新功能都应在新的快照/分支上进行；不要直接修改snapshots/personal-mvp-v1.0-2026-11-12。
