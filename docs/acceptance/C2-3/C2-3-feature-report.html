2. 对外 API 与数据结构

2.1 导出

模块挂载在 globalThis.BiliDailyCandidateFeatures，整体冻结：

globalThis.BiliDailyCandidateFeatures = Object.freeze({
  UNKNOWN_PARTITION,        // "未知"
  DEFAULT_THRESHOLDS,       // 默认阈值（冻结对象）

2.2 主入口

buildCandidateFeatures(records, pool, options)
  • records：biliDailyRecords 根结构 { version, days }，或直接的“日期 → 记录表”映射。
  • pool：支持三种形态：
  • 候选数组；
  • C2-1 / C2-2 的 { candidates: [...] }；
  • C2-2 filterEligibleCandidates 的 { eligible, review, excluded }，元素可以是 { candidate, assessment } 或裸候选对象。
  • options.thresholds：覆盖 DEFAULT_THRESHOLDS。只接受有限、非负数值；覆盖率阈值钳制在 0..1，数量 / 长度上限取整且不小于 1。
  • options 中无法识别的键被忽略，不产生副作用。

3. 分区特征的计算方式

3.1 数据来源与去重

  1. 通过 stats.cleanRecord 清洗每条记录，复用既有的字段规则、UID 规范化与watchMs 安全转换。
  2. 通过 stats.mergeByBvid 合并同一 BV 的同日重复、跨天记录与多分 P：一个 BV 只算一个视频，watchMs 累加。
  3. 记录没有 BV 时无法可靠去重，跳过并计入 diagnostics.recordsWithoutBvid，不把多条无 BV 记录合并成一个虚构视频。

3.2 时长加权

  • 每个已识别分区累加真实 watchMs，不使用 videoDuration。
  • shareOfIdentified = 分区 watchMs / identifiedWatchMs，即“已识别分区内部”的占比，已识别分区之和为 1。
  • shareOfAll = 分区 watchMs / observedWatchMs，分母包含未知分区，用于观察该分区在全部真实观看中的份额。
  • 分区列表按 watchMs 降序、再按分区名字符串升序排序，结果确定。

3.3 未知分区

以下情况统一归入 "未知" 桶，真实时长仍保留在分母中：

  • 非字符串；
  • 空字符串或仅空白；
  • 字面值 "未知"；
  • 含控制字符、零宽字符或双向格式字符；
  • 按 Unicode 码点超过 maxPartitionLength（默认 64）；
  • 为防御异常大输入，UTF-16 长度超过 maxPartitionLength * 2 时提前拒绝。

未知桶的 shareOfIdentified 固定为 0（它不属于已识别分区），shareOfAll = unknownWatchMs / observedWatchMs。

3.4 覆盖率

partitionCoverage = identifiedWatchMs / observedWatchMs
  • 分母是全部真实观看时长，包含未知分区，不会把缺失数据悄悄排除。
  • 无任何有效观看时长时为 null，同时 partitionCoverageState = "no-data"；不会伪装成 0% 或 100%。
  • missingPartitionCount 记录进入未知桶的视频数。

4. 标题 bigram 规则

4.1 确定性归一化

normalizeTitle 的顺序固定：

  1. 非字符串 → 视为空标题，不猜测；
  2. 原始字符串超过 maxTitleRawLength（1000 个 UTF-16 单元）时截断，并避免截断在 UTF-16 代理对中间；
  3. 尝试 NFKC（如全角 ＡＩ → AI）；环境不支持时保留原文，不丢标题；
  4. 控制字符、零宽字符、双向控制符替换为空格（不是删除），避免两侧字符粘连；
  5. 去除首尾空白，Latin 字母统一小写；
  6. 按 Unicode 码点截断到 maxTitleLength（默认 200）。

4.2 分词与 bigram

  • 词内字符定义为 Unicode \p{L}（字母）、\p{N}（数字）、\p{M}（组合附加符）。
  • 其余字符（标点、空白、emoji、符号）一律作为分隔符。
  • 对每个连续段，取相邻两字符组成 bigram；不跨标点或空白拼接。
  • 单字符段不产生 bigram（例如标题只有“猫”时词元为空）。
  • 中文、英文、数字、混合标题使用同一规则，不做额外分词或词典匹配。

示例：

标题生成的 bigram（节选）
科技前沿科技、技前、前沿
AI 2026ai、20、02、26
Hello,世界!he、el、ll、lo、世界

英文按字符 bigram 处理，不切分为完整单词；这是本阶段的明确口径。

4.3 词频与文档数

  • 同一视频内重复出现的词元：count 累计，documentCount 只加 1。
  • 同一 BV 的重复观看、跨天观看、多分 P 已在 3.1 合并为一个视频，因此不会因重复观看而重复累计词元或文档数。
  • 每个候选最多保留 maxUniqueTokens（默认 4000）个不同词元；达到上限后不再接收新词元，已有词元继续累计，并置 tokenMapOverflow = true。
  • 输出最多 maxOutputTokens（默认 2000）个词元，按 count 降序、再按词元字符串升序排序；被截断时 outputTruncated = true。
  • uniqueTokenCount 是词表实际大小；totalTokenCount 是所有词元出现次数之和；documentCount 是至少生成一个 bigram 的视频数。

4.4 标题覆盖率

titleCoverage = titledVideoCount / observedVideoCount
  • 分母是参与统计的视频数（去重、无冲突、watchMs > 0）。
  • 分子只统计至少能生成一个 bigram 的视频；缺失标题、归一化后为空、只有单字符而无 bigram 的视频都不计入分子。
  • 无任何参与统计的视频时，覆盖率为 null，状态为 "no-data"。

5. UID 与 BV 的身份 / 去重规则

5.1 只认 UID

  • 所有归属只使用规范化后的 upUid，复用 stats.cleanRecord 的规则：正整数、安全整数、统一为字符串。
  • 昵称不参与身份判定：同一 UID 改名仍合并；不同 UID 同名严格分开。
  • 缺失 UID 的旧记录不会凭昵称并入任何候选；它们只计入diagnostics.uidlessVideos。这是有意的保守策略，避免把旧记录错误归属。

5.2 BV 去重

  • 同一 BV 无论出现在同一天多次、跨天、不同分 P，均通过 mergeByBvid合并为一个视频，watchMs 累加。
  • 重复观看不会让 observedVideoCount、documentCount 或词频虚假膨胀。
  • observedVideoCount 只统计 watchMs > 0 的视频；watchMs <= 0 的记录进入 diagnostics.zeroWatchVideos，不参与特征统计。

5.3 与 C2-1 / C2-2 的关系

  • 本模块不修改 C2-1 的 watchedVideoCount、watchedWatchMs 等观看计数。
  • 本模块不修改 C2-2 的 eligible / review / excluded 结论。
  • featureStatus 与 C2-2 资格是正交维度：特征不完整不会自动降级 C2-2 资格，C2-2 的冲突结论也不会被本模块改写。
  • 测试 32 明确验证：冲突候选的 C2-2 资格结论在特征计算前后保持一致。

6. 同 BV 多 UID 冲突处理

6.1 独立检测

本模块不信任 C2-1 的“先出现者”归属。扫描记录时单独建立BV → Set(UID)，只要同一 BV 出现 ≥2 个不同有效 UID，就把该 BV 标记为冲突视频。

6.2 保守策略

对冲突 BV：

  • 不计入任何一方的分区特征；
  • 不计入任何一方的标题特征；
  • 不计入任何一方的 observedVideoCount / observedWatchMs；
  • 每个涉及该 BV 的池内候选，conflictVideoCount 加 1，hasUidConflict = true；
  • 只保留在诊断中：diagnostics.uidConflictVideos（唯一 BV 数）、diagnostics.conflictVideosSeen（扫描到的冲突视频数）；
  • 跨候选汇总的 summary.conflictVideoCount 使用唯一冲突 BV 数，避免同一 BV 涉及两个 UID 时被重复计算。

6.3 为什么整体排除

同一 BV 被记录成两个 UID 时，无法从本地数据判断谁是真实 UP 主。把该视频分配给任意一方都会制造虚假内容特征；整体排除只会损失少量数据，但能保证“所有进入特征的分区 / 标题都来自可信归属”。冲突本身仍可诊断，不会静默消失。

身份冲突只产生 level: "info" 的原因 uid-conflicts-excluded，不会单独把 featureStatus 降级，也不会改变 C2-2 资格。

15. 已知限制与 C3 的数据需求

15.1 已知限制

  1. 只做特征，不做排序：没有 TF-IDF、余弦相似度、MMR、时间衰减或个性化评分。
  2. 英文按字符 bigram：Hello 会生成 he / el / ll / lo，不是完整单词；本阶段不引入分词器或词典。
  3. 标题是词面特征：无法识别同义词、语义或反讽；标题党、重复标题会直接反映在词频中。
  4. 缺失 UID 的旧记录被排除：这是身份安全策略的代价，可能损失部分老数据。
  5. 冲突视频整体排除：若冲突来自采集 bug，会损失该视频的全部特征；目前只在诊断中暴露，不做自动修复。
  6. 覆盖率阈值是启发式：2 个视频 / 5 分钟 / 50% 只是保守起点，尚未用真实分布校准。
  7. 无真实数据验证：本阶段禁止读写 chrome.storage.local，所有测试均为固定夹具；合成性能数字不代表真实规模。
  8. featureStatus 不是兴趣强度：ready 只表示数据条件满足，不代表用户真的喜欢该 UP 主。
  9. 分区与标题依赖记录字段：如果记录本身缺失分区或标题，本模块不会从页面、API 或昵称反推。

15.2 C3 需要补齐的输入

  • 明确的排序目标与评价口径（例如：回访概率、观看时长、分区多样性）。
  • 真实数据上的特征分布抽样，用于校准覆盖率阈值与样本量阈值。
  • 对冲突视频的人工 / 规则复核流程，决定是否可以恢复部分归属。
  • 时间衰减、分区偏好、词元权重的设计文档与验收标准。
  • 若要做语义特征，需要另行评审是否引入模型或词典；本阶段明确未引入。
  • UI / 存储 / 新采集均未开始，需在 C3 或后续阶段单独评审。
